# Аудит производительности и потенциальных утечек памяти (DVClient)

Первичный аудит: 2026-04-07. Повторная проверка кода и доработка: 2026-10-08.

## Проверенные направления

- Жизненный цикл `Fragment`/`Activity`: очистка `WebView`, подписок `EventBus`, обработчиков и фоновых задач.
- HTML в списках: форматирование, ссылки, списки, картинки и entities, включая `&#x20;`.
- Повторное использование `RecyclerView.ViewHolder`, доставка результатов при быстром скролле и повторном подключении адаптера.
- Границы кэшей и очередей, статические ссылки на UI, мониторинг `DownloadManager`.
- Список личных сообщений, полный просмотр и надёжное отложенное удаление.

## Реализовано при повторной проверке

### HTML-рендер списков

`AsyncHtmlRenderer` применяется в `AdapterForumPosts`, `AdapterComments`, `AdapterMainRazdel`, а также в списках личных сообщений и друзей.

1. `Html.fromHtml()` работает на отдельном потоке. Очередь ограничена 24 ожидающими задачами; избыточные запросы текущих представлений подхватываются после завершения уже поставленных задач.
2. Общая задача для одинакового HTML доставляет результат каждому ещё ожидающему `TextView`. При обновлении или recycle прежний результат не может попасть в другой элемент.
3. `LruCache` ограничивается суммарной длиной исходного/отрендеренного текста и оценкой количества spans, а не только числом сообщений. Ключ — полный исходный HTML: коллизии `String.hashCode()` не смешивают содержимое.
4. Кэш содержит шаблоны `Spanned` без ссылок на `TextView`, `Activity` или сетевые загрузчики картинок. Entities декодируются штатным HTML-парсером; оформление, списки и ссылки сохраняются.
5. До завершения разбора выводится пустой текст; теги и entities не мелькают как исходный HTML. Синхронная тяжёлая HTML-обработка не возвращается как fallback при переполнении очереди.
6. Для комментариев и полного просмотра ЛС картинки подключаются после парсинга через отдельные mutable spans и Glide targets конкретного представления. Результаты и изображения не разделяются между переиспользованными holder. Для компактных превью и рангов загрузка inline-картинок отключена.
7. `clear()` отменяет картинки и доставку отдельного target; `release()` очищает кэш/очередь, останавливает executor и инвалидирует поколение уже выполняющегося парсинга. `activate()` поддерживает повторное подключение того же адаптера.

Синхронный `Html.fromHtml()` в действии «копировать текст» остаётся: это явная команда пользователя, не путь bind при скролле. Полноэкранные страницы файлов и существующий `URLImageParser` за пределами этих списков не переработаны.

### Основной список и read marks

- HTML-задачи не конкурируют с запросами Room в общем executor приложения.
- Кэш read marks ограничен, потокобезопасен и восстанавливает вытесненные записи по запросу при длинном листании; одинаковые запросы дедуплицируются.
- Фоновая загрузка работает со снимком списка; устаревшие callback после cleanup не обновляют уходящий экран.
- Обновления read marks используют payload и не запускают полный rebind текста и изображений всех видимых строк.
- На detach/cleanup сохраняются накопленные отметки, даже если их меньше десяти.
- Действия удаления/модерации используют текущую позицию holder и учитывают `NO_POSITION`; stable ID объединяет section и server ID в 64 битах.

### Мониторинг загрузок

`DownloadBroadcastReceiver` хранит общий реестр задач по ID загрузки и application context. Запросы `DownloadManager` выполняются на одном фоновом потоке; `onReceive()` использует `goAsync()`.

Монитор отменяется при завершении/ошибке, исчезновении записи, недоступном сервисе/курсоре, ошибке запроса, отсутствии возможности показать уведомление или по истечении шести часов. Отдельные notification tags исключают перезапись уведомлений разных загрузок. Публичный `stopProgressMonitoring(downloadId)` отменяет только монитор, сохраняя системную загрузку.

`startProgressMonitoring()` в исходном проекте не вызывался из `DownloadFile`; это состояние сохранено. Ограничения и отмена проверены для самого API мониторинга. Реальные загрузки и уведомления на устройстве требуют отдельной проверки.

### Личные сообщения

- Компактные строки показывают аватар, собеседника, дату, тему, превью и отметку непрочитанного. Полный HTML и форма ответа открываются отдельным bottom sheet; состояние формы не хранится в переиспользуемом holder.
- Серверные страницы по 10 элементов объединяются в непрерывный список. Один запрос одновременно, продвижение после успеха, повтор той же страницы после ошибки и дедупликация по ID. После удаления перечитывается перекрывающаяся страница, поскольку сервер использует `LIMIT` с offset.
- `AdapterPm` и `AdapterPmFriends` используют `AsyncListDiffer`, stable ID и копии данных перед сравнением. Подробный HTML и изображения не разбираются при bind компактной строки.
- Черновики, вложения и read flags принадлежат аккаунту и ID строки. Смена аккаунта синхронно очищает committed list, отменяет прежние diff/HTML callbacks и закрывает форму. Callback выбора картинки связан с конкретной формой и сохраняет эту связь при пересоздании `Activity`.
- Для исходящих сообщений сохраняются исходный отправитель и получатель: отправка выполняется через проверенный точный UID получателя, а не через reply API, который отвечает `user_from`. Неудачный поиск получателя сохраняет просмотр и черновик, предоставляет явный повтор и блокирует отправку.
- Удаление сначала сохраняется в отдельной SQLite-очереди в `noBackupFilesDir`, затем строка скрывается локально. `WorkManager` восстанавливает задачи после завершения процесса; удаление из уведомления использует `goAsync()` и закрывает уведомление после сохранения задачи.
- «Ответить и удалить» сначала получает положительный ответ отправки, затем использует ту же очередь удаления. Отказ отправки не ставит удаление в очередь; отказ сохранения очереди не вызывает повторную отправку ответа и оставляет строку видимой.
- Первая попытка запускается сразу. После ошибки следующий запуск назначается через 10 минут, последующие — через 30 минут, максимум 6 часов с момента исходного действия. Android может отложить запуск фоновой задачи; проверка абсолютного срока исключает запрос удаления после его истечения.
- Задача привязана к аккаунту и ID сообщения. Пароль не сохраняется в SQLite или WorkManager; перед запросами проверяется текущий аккаунт и серверная авторизация. Истёкшие неподтверждённые операции перестают скрывать сообщение при обновлении.
- Новое явное удаление после истечения срока получает новое поколение намерения и собственный срок; завершение старого воркера не удаляет и не перезаписывает новую операцию. Повторное нажатие в пределах действующей операции не продлевает её срок.
- PHP API повторно меняет счётчики даже для уже удалённой строки. Перед повторной мутацией воркер подтверждает наличие сообщения в активной папке; после потери ответа проверяет корзину. HTTP-транспорт запрещает скрытые повторы и redirects. Полную гарантию exactly-once при одновременном удалении другим клиентом может дать только серверная идемпотентность.
- Счётчик непрочитанных обновляется по ответу авторизации сервера; повторное открытие уже прочитанного сообщения не уменьшает его локально повторно.

## Проверки и оставшиеся действия

- Добавлены `AsyncHtmlRendererTest` для HTML entities/оформления/ссылок/списков, доставки одинакового источника нескольким views, recycle, release/reattach, переполнения очереди, отсутствующего текста и раздельных drawable для картинок из кэша.
- Тесты очереди проверяют сохранение и восстановление намерения удаления, интервалы и предел 6 часов, таймаут после фактической мутации, смену аккаунта, отрицательные/неоднозначные ответы API и отказ планировщика. Локальный HTTP-сервер проверяет отсутствие повторов при обрыве соединения и `503 / Retry-After: 0`; receiver проверяется с настоящей записью в SQLite и очередью WorkManager.
- Тесты пагинации проверяют ошибки, повторные запросы, завершение списка и смещение страниц после удаления. Robolectric-проверки формы охватывают сохранение черновика при ошибке, вложения и смену аккаунта.
- Для `DownloadBroadcastReceiver` Robolectric проверяет исчезновение/завершение записи, отмену только своего монитора, раздельные уведомления и отсутствие дальнейшего поллинга при запрете уведомлений.
- Выполнены сборка Google Debug APK, 72 unit/Robolectric-теста (0 ошибок и пропусков), проверка подписи APK v2 и Android Lint (0 ошибок, 642 предупреждения, 2 подсказки). Использованы закреплённые JDK 21, Gradle 9.8.0 и SDK 37; команды и ограничения проверки указаны в PR. `git diff --check` прошёл.
- Измерения frame time, memory profiler/LeakCanary и испытания реального интернета/авиарежима на устройстве ещё не выполнены. Ускорение обосновано удалением тяжёлого парсинга из bind и ограничением задач; численное снижение jank не заявляется.
- `DialogFragment` вместо `ProgressHelper` — опциональная следующая итерация, не выполнена в текущей доработке.
