# Совместимость с размером страницы памяти 16 КБ

Аудит выполнен 9 октября 2026 года для `DVClient_Google`, `versionCode 300000086`, `versionName 5.0-google`, AGP `9.4.1`, `minSdk 27`, `targetSdk 37`.

## Два отдельных результата расследования

Полный стек сбоя, полученный после уведомления Google Play, указывает на Java `NullPointerException` в `NetworkUtils.getEncodedAuthData()`: код вызывает `Context.getString()` при `context == null`. Путь вызова — действие «В новости» в меню карточки, `AdapterMainRazdel` → `NetworkUtils.putToNews()` → проверка логина и пароля. Недостаточный или отсутствующий логин/пароль запускает ошибочную ветку. Аналогичный путь существовал в `getOdob()`. Такой сбой может произойти на устройстве с любым размером страницы памяти; он сам по себе не доказывает ошибку загрузчика ELF. Строка `SystemUptimeMs` без полного стека не позволяет определить причину.

Проверка учётных данных теперь использует контекст приложения. Операции одобрения и переноса в новости получают контекст вызывающего экрана и переводят его в контекст приложения для ответа. Старые варианты методов без параметра контекста сохраняются и используют `AppController`. Неуспешная проверка показывает соответствующее уведомление и не отправляет запрос. Обратные вызовы Volley также используют контекст приложения вместо статического `MainActivity.binding`, поэтому успех или сетевая ошибка не требуют существования прежнего окна. Раздел, ID материала и URL-кодирование учётных данных сохранены.

Отдельный анализ упакованных библиотек выявил необходимость обновления DataStore. Собственного JNI-кода у приложения нет, но Firebase транзитивно включает DataStore и `libdatastore_shared_counter.so`. У прежней DataStore `1.1.7` все `PT_LOAD` имеют выравнивание `0x4000` (16 КБ), а несжатые библиотеки в debug APK уже начинались на границе 16 КБ. Однако конец `GNU_RELRO` не был кратен 16 КБ. Текущая [официальная инструкция Android](https://developer.android.com/guide/practices/page-sizes) отдельно требует проверять этот диапазон защиты памяти: неправильное выравнивание может вызвать сбой во время выполнения.

| ABI | `PT_LOAD` в 1.1.7 | Конец `GNU_RELRO` в 1.1.7 | Конец `GNU_RELRO` в 1.2.1 |
| --- | --- | --- | --- |
| arm64-v8a | `0x4000` | `0x6000`, не кратен 16 КБ | `0xc000`, кратен 16 КБ |
| armeabi-v7a | `0x4000` | `0x5000`, не кратен 16 КБ | `0xc000`, кратен 16 КБ |
| x86 | `0x4000` | `0x5000`, не кратен 16 КБ | `0xc000`, кратен 16 КБ |
| x86_64 | `0x4000` | `0x6000`, не кратен 16 КБ | `0xc000`, кратен 16 КБ |

Приложение задаёт стабильную DataStore `1.2.1` через зависимости `datastore` и `datastore-preferences`, обновляя общий Android core и его нативную библиотеку. В 1.2.1 все ABI имеют также правильное выравнивание `PT_LOAD`. Версия [выпущена 11 марта 2026 года](https://developer.android.com/jetpack/androidx/releases/datastore#1.2.1); в официальных заметках указаны инфраструктурные исправления. Предварительная версия не требуется. Этот результат не означает, что прежний нативный код вызвал предоставленный Java-сбой: для того стека исправляется контекст.

## Повторяемая проверка выпуска

Собрать именно Google release APK и Android App Bundle с установленными JDK/Android SDK:

```bash
./gradlew :app:assembleDVClient_GoogleRelease :app:bundleDVClient_GoogleRelease
./gradlew :app:testDVClient_GoogleDebugUnitTest :app:lintDVClient_GoogleRelease
```

Обычная release-сборка использует настроенную в проекте подпись. В облачной среде для проверки применяется временная отладочная подпись через внешние параметры Gradle; ключ публикации не используется и конфигурация подписи проекта не меняется. Проверенные облачные артефакты не предназначены для прямой загрузки в Google Play вместо выпуска со штатным ключом.

Проверить артефакты скриптом из репозитория; достаточно Python 3.9+:

```bash
python3 tools/check_android_16kb.py \
  app/build/outputs/apk/DVClient_Google/release/app-DVClient_Google-release.apk \
  app/build/outputs/bundle/DVClient_GoogleRelease/app-DVClient_Google-release.aab
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tools/tests -v
```

Скрипт разбирает ELF32/ELF64 и проверяет:

- Выравнивание `PT_LOAD` — степень двойки не менее `16384`; смещение в файле и виртуальный адрес должны совпадать по модулю `16384`.
- Конец `GNU_RELRO`: `(VirtAddr + MemSiz) % 16384 == 0`.
- У несжатых `.so` в APK начало данных локальной ZIP-записи кратно `16384`. Сжатые библиотеки всё равно проходят проверку ELF, но не требуют такого ZIP-смещения: они извлекаются при установке.
- Повреждённые ELF/ZIP завершают проверку ошибкой. APK без нативных библиотек не требует нативного выравнивания.

У AAB не проверяются ZIP-смещения библиотек: его архив не является установленным APK. Отдельно проверить конфигурацию bundletool:

```bash
java -jar /path/to/bundletool-all.jar dump config \
  --bundle=app/build/outputs/bundle/DVClient_GoogleRelease/app-DVClient_Google-release.aab
```

Поле `alignment` должно иметь значение `PAGE_ALIGNMENT_16K`. AGP `9.4.1` уже выше необходимой версии `8.5.1`; менять режим упаковки на устаревший сжатый вариант не требуется. APK, включая APK, созданный из AAB через bundletool, дополнительно проверить официальным инструментом Android SDK:

```bash
"$ANDROID_SDK_ROOT/build-tools/37.0.0/zipalign" -v -c -P 16 4 \
  app/build/outputs/apk/DVClient_Google/release/app-DVClient_Google-release.apk
```

При корректной упаковке последняя строка — `Verification successful`.

## Выполнено и остаётся проверить

Собраны Google release APK и AAB. Оба прошли проверку ELF всех четырёх ABI новым скриптом; у AAB подтверждено `PAGE_ALIGNMENT_16K`. Release APK и универсальный APK, созданный из этого AAB через bundletool `1.18.3`, прошли проверку ZIP-выравнивания `zipalign -c -P 16 4` и проверку подписи `apksigner`. Семейство DataStore в release runtime classpath разрешилось в `1.2.1`.

Прошли все 251 Android unit test без пропусков, включая восемь новых регрессий для реального действия меню «В новости», отсутствующего логина/короткого пароля, параметров запроса, старых публичных вариантов методов, успешного ответа и сетевой ошибки после уничтожения Activity. Robolectric `4.17` на API 36 требует доступа к `jdk.internal.access` для настройки Android shared memory: экспорт добавлен только к JVM unit tests, на код приложения не влияет. Прошли также 16 тестов Python для ELF32/ELF64, повреждённых данных, неверных LOAD/RELRO, ZIP-упаковки и AAB. Release lint завершился без ошибок; остаются 642 предупреждения и две подсказки.

Статическая проверка артефакта и Robolectric не заменяют запуск на устройстве с 16 КБ. Физического устройства и Android-эмулятора в облачной среде нет; такой запуск здесь не выполнялся. Для ручной проверки использовать совместимое устройство либо образ Android 15/16 с 16 КБ и сначала подтвердить размер страницы:

```bash
adb shell getconf PAGE_SIZE
```

Ожидается `16384`. Установить APK штатной release-сборки, запустить приложение без сохранённого аккаунта и с правильным аккаунтом, открыть меню материала и выбрать «В новости»/одобрение, затем проверить успешный ответ и отсутствие сети. Проверить также холодный запуск, обновление ленты и получение push: эти сценарии позволяют обнаружить ошибки загрузки транзитивной нативной библиотеки и ошибки контекста. Затем повторить тест Google Play для нового `versionCode 300000086` и сопоставить полный стек оставшихся сбоев с конкретным действием. Исчезновение предупреждения Play по одной статической проверке не заявляется.
